### 면접 예상 질문 및 답변 (Interview Q&A)

#### 질문 1: 이 프로젝트의 전반적인 아키텍처와 데이터 흐름에 대해 설명해주세요.

**답변:**
이 프로젝트는 MySQL의 변경 데이터를 실시간으로 캡처하여 Kafka로 스트리밍하고, Spark Structured Streaming으로 처리하여 최종적으로 운영 및 리스크 지표를 집계하는 End-to-End CDC 파이프라인입니다.

데이터 흐름은 다음과 같습니다.
1.  **MySQL & Debezium:** 운영 데이터베이스인 MySQL에서 주문, 고객, 상품 데이터의 변경(INSERT, UPDATE, DELETE)이 발생하면, Debezium 커넥터가 이를 binlog를 통해 감지하여 CDC 이벤트를 생성합니다.
2.  **Kafka:** Debezium은 이 CDC 이벤트를 JSON 형태로 Kafka 토픽에 발행합니다. 각 테이블별로 별도의 토픽이 사용됩니다.
3.  **Spark Structured Streaming:** 3개의 Spark 스트리밍 잡이 병렬로 실행됩니다.
    *   **`stream_cdc.py`**: Kafka의 모든 CDC 이벤트를 읽어 원시(raw) 데이터 형태로 Parquet 파일에 저장합니다. 이는 데이터 레이크를 구축하고, 원본을 보존하여 추후 분석이나 재처리를 위함입니다.
    *   **`stream_a1_orders.py`**: 주문 관련 토픽을 구독하여, 10초 tumbling window 기준으로 분당 주문 건수를 집계하고, 그 결과를 MySQL의 `minute_order_summary` 테이블에 저장합니다.
    *   **`stream_b1_cancel_rate.py`**: 주문 상태 변경 이벤트를 활용하여, 1분 sliding window 기준으로 실시간 취소율을 계산하고, `ten_minute_cancel_rate` 테이블에 저장합니다.
4.  **Event Replayer:** 정적 데이터셋(Olist)의 한계를 극복하기 위해, 과거 데이터를 실제 트래픽처럼 시뮬레이션하는 `replay_orders.py` 스크립트를 구현했습니다. 이 스크립트는 원본 데이터의 타임스탬프 간격을 비례적으로 압축하여 MySQL에 순차적으로 INSERT/UPDATE를 실행함으로써, 실제와 유사한 연속적인 CDC 이벤트 스트림을 생성합니다.

**꼬리 질문:**
1.  Debezium이 MySQL의 변경 데이터를 어떻게 감지하는지 그 원리를 좀 더 자세히 설명해주시겠어요? (binlog, replication protocol)
2.  Spark 스트리밍 잡을 3개로 분리하여 운영하신 특별한 이유가 있나요? 하나의 잡에서 모두 처리할 수도 있었을 텐데요. (관심사 분리, 독립적 확장/배포)
3.  Event Replayer가 생성하는 트래픽이 실제 운영 환경의 트래픽 패턴을 잘 반영한다고 어떻게 확신할 수 있나요? (burst/lull 패턴 보존, 시간 압축의 한계)

#### 질문 2: 이 프로젝트의 데이터 규모는 약 50MB 정도로, Spark를 사용하기에는 다소 작아 보입니다. 그럼에도 불구하고 Spark Structured Streaming을 선택하신 이유는 무엇인가요?

**답변:**
좋은 지적입니다. 프로젝트를 진행하면서 저 또한 동일한 질문을 스스로에게 던졌고, 이는 ADR-009에 상세히 기록되어 있습니다. 결론부터 말씀드리면, **처리 성능 때문이 아니라, Spark의 스트리밍 처리 방식, 특히 '정확성(Correctness)'과 '복원성(Resiliency)' 관련 기능을 학습하고 검증하기 위해** 전략적으로 Spark를 사용했습니다.

이 프로젝트의 데이터 규모(~50MB)만 고려하면, 초기 데이터 적재는 `pandas`로, 스트리밍 처리는 `confluent-kafka` 같은 Python 라이브러리로도 충분히 구현 가능합니다. 실제로 초기 70% 데이터 적재는 Spark의 JVM 오버헤드를 피하기 위해 의도적으로 `pandas`를 사용했습니다(ADR-001).

하지만 스트리밍 처리에서 Spark를 유지한 이유는 다음과 같습니다.
1.  **Exactly-Once Semantics 검증:** Spark가 제공하는 체크포인트(checkpoint)와 멱등성(idempotent) sink(Parquet) 조합을 통해, 어떻게 이벤트 유실이나 중복 없이 '정확히 한 번' 처리를 보장하는지 실제 코드로 구현하고 검증하고 싶었습니다.
2.  **장애 복구 시나리오 테스트:** Kafka나 Spark 드라이버가 예기치 않게 종료되었을 때, 체크포인트로부터 마지막 처리 상태를 복원하여 중단된 지점부터 스트림을 재개하는지 확인하는 것이 중요했습니다. `verify_restart_recovery.py` 스크립트를 통해 이를 실제로 검증했습니다.
3.  **상태 기반 처리(Stateful Processing) 학습:** 실시간 취소율(B1 지표) 계산에 사용된 sliding window와 같은 상태 기반 스트림 처리 로직을 Spark의 고수준 API를 통해 경험하고 싶었습니다.

따라서 면접관님 말씀처럼 이 프로젝트에서 Spark는 '망치를 들기 위해 견과류를 사용하는' 것처럼 보일 수 있지만, 저의 목적은 '견과류를 깨는 것'이 아니라 '망치(Spark)의 사용법과 특성을 제대로 익히는 것'에 있었습니다.

**꼬리 질문:**
1.  말씀하신 '체크포인트'에는 구체적으로 어떤 정보들이 저장되며, 장애 복구 시 어떻게 사용되나요? (오프셋, 상태 저장소, commit 로그)
2.  만약 이 파이프라인을 실제 프로덕션 환경에 더 큰 규모로 배포해야 한다면, 현재 아키텍처에서 어떤 부분을 변경하거나 추가로 고려하시겠습니까? (Spark 클러스터 모드, 리소스 튜닝, Kafka 파티셔닝)
3.  Python Consumer와 비교했을 때, Spark Structured Streaming을 사용하면서 느낀 가장 큰 장점과 단점은 무엇이었나요? (높은 추상화 수준 vs JVM 오버헤드 및 복잡성)

#### 질문 3: 프로젝트에서 '실시간 취소율'이라는 리스크 지표를 구현하셨습니다. 이 지표가 왜 CDC(Change Data Capture) 파이프라인의 필요성을 잘 보여주는 사례라고 생각하시나요?

**답변:**
'실시간 취소율'(B1 지표)은 **단순 INSERT만으로는 계산할 수 없고, 데이터의 상태 전이(state transition), 즉 UPDATE를 포착해야만 의미가 있는 지표**이기 때문입니다. 이는 ADR-013에서 v2 지표 파이프라인을 설계할 때 가장 중요하게 고려했던 점입니다.

만약 저희가 CDC가 아닌, 애플리케이션 로그를 Kafka로 보내는 방식(INSERT-only)을 사용했다고 가정해 보겠습니다. 주문이 생성될 때(`order_status='created'`) 로그가 한 번 발생하고, 나중에 고객이 주문을 취소하여 `order_status`가 'canceled'로 변경되어도, 이 변경 사실을 별도의 로그로 남기지 않는 한 파이프라인은 알 수 없습니다.

하지만 CDC는 다릅니다. Debezium은 데이터베이스의 binlog를 직접 읽기 때문에, `UPDATE orders SET order_status = 'canceled' WHERE order_id = ?` 라는 SQL이 실행되면, 이를 `op='u'` (update) 이벤트로 포착합니다. 이 이벤트의 `payload`에는 변경 전(`before`) 상태와 변경 후(`after`) 상태가 모두 담겨 있습니다.

저의 `stream_b1_cancel_rate.py` 잡은 바로 이 `op='u'` 이벤트를 필터링하고, `before.order_status`는 'shipped'였는데 `after.order_status`가 'canceled'로 변경된 건들을 '취소'로 집계합니다.

이처럼 **'실시간 취소율'은 CDC를 통해 데이터의 '변경 이력' 자체를 스트리밍 데이터로 활용할 때 비로소 계산 가능한 지표**입니다. 이는 CDC가 단순히 데이터를 복제하는 것을 넘어, 비즈니스적으로 가치 있는 새로운 인사이트를 실시간으로 제공할 수 있음을 보여주는 강력한 예시라고 생각합니다. 이 지표를 구현함으로써, "왜 굳이 복잡한 CDC를 써야 하는가?"라는 질문에 "이런 지표는 CDC가 아니면 만들 수 없기 때문입니다"라고 명확하게 답할 수 있게 되었습니다.

**꼬리 질문:**
1.  UPDATE 이벤트 외에 DELETE 이벤트를 활용하여 구현할 수 있는 흥미로운 지표는 어떤 것이 있을까요? (회원 탈퇴율, 상품 단종에 따른 영향 분석)
2.  취소율 계산 시, `order_status`가 여러 단계를 거쳐 변경될 수 있습니다. (예: `processing` -> `shipped` -> `canceled`). 이러한 복잡한 상태 전이를 어떻게 처리하셨나요? (이 프로젝트에서는 shipped->canceled로 단순화, 실제로는 상태 전이 모델(FSM) 고려)
3.  실시간 취소율이 특정 임계치를 넘었을 때, 자동으로 알람을 보내는 시스템을 구축한다면 어떻게 설계하시겠습니까? (Spark 스트림 결과를 다른 Kafka 토픽으로 보내거나, MySQL 저장 후 별도 모니터링 시스템 연동)
